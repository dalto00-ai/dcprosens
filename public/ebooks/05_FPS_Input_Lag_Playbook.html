THE LATENCY CHAIN ARCHITECTURE
TELEMETRY DECONSTRUCTION

FPS is not input lag.

High frames per second does not guarantee low latency. Three distinct questions require three different types of empirical evidence.

THE 4-STAGE LOCAL LATENCY PIPELINE
01 / INPUT
Device Sensor
Microswitch contact, MCU debounce filter, USB polling interval (1000–8000Hz).
02 / ENGINE
Game Simulation
OS message pump, DirectX input poll, game tick calculation, player position state.
03 / RENDER
GPU Pipeline
Driver command queue, shader execution, rasterization, swapchain back-buffer flip.
04 / DISPLAY
Photon Scanout
Display scaler buffer, vertical scanout lines, liquid crystal GtG transition.
Metric What It Actually Proves What It Does NOT Prove
Average FPS Raw throughput: how many total frames were rendered across the entire sample window. Does not prove frame consistency, zero stutter, or low input latency.
Frame Times / 1% Low Pacing consistency: reveals hitching, render queue stalls, and micro-stutters. Does not measure end-to-end mouse-to-display photon latency.
End-to-End Latency True latency: duration between physical microswitch click and photon emission on monitor. Does not prove network tickrate stability or server-side hitreg.

EXPERIMENT 01 // PROTOCOL BASELINE
SCIENTIFIC METHODOLOGY

Build a baseline you can repeat.

Testing during a live multiplayer match yields random noise, not clean data. Establish a strictly controlled practice run first.

FRAME-TIME PACING COMPARISON (SYNTHETIC BENCHMARK TRACE) VERTICAL AXIS = MS PER FRAME (LOWER IS BETTER)
1

Select a 100% Repeatable Benchmark Scene

Use an integrated game benchmark tool or a fixed empty practice map route. Keep resolution, FOV, viewing angles, and capture duration identical.

2

Allow Thermal & Shader Equilibrium

Never record immediately upon launching. Let shaders finish caching and wait 5 minutes until GPU/CPU clocks reach stable operating temperatures.

3

Capture Three 60-Second Runs (Median Rule)

Run three distinct 60-second telemetry passes (CapFrameX or PresentMon). Take the median result, never cherry-pick the single best score.

4

Log Full Context Metadata

Document GPU driver version, Windows build number, background capture processes, and in-game render resolution scale alongside your numbers.

MEASURE CONSISTENTLY

Different tools calculate 1% lows differently (pure percentiles vs average of lower percentiles). Always use the exact same software version for both Baseline and Test.

THE A/B/A VERIFICATION RULE

If an apparent gain is within standard run-to-run noise (±2-3%), treat it as inconclusive. Revert back to A and re-test to verify causation.

EXPERIMENT 02 // WINDOWS GRAPHICS STACK
OPERATING SYSTEM TUNING

Make reversible Windows changes.

Tune official, documented OS presentation pipelines. Always preserve your default configuration before modifying flags.

WINDOWS 11 GRAPHICS PIPELINE ARCHITECTURE (OFFICIAL SETTINGS) WDDM 3.0+ COMPATIBLE
OPTIMIZATIONS FOR WINDOWED GAMES
Upgrades legacy DirectX 11 presentation to modern DXGI flip-model presentation, reducing borderless latency to match exclusive fullscreen. [Ref: 2]
HARDWARE-ACCELERATED SCHEDULING (HAGS)
Hands thread command arbitration directly to dedicated GPU scheduling processors, bypassing Windows CPU scheduler overhead.
WINDOWS GAME MODE
Prioritizes CPU thread allocation to the foreground game process while strictly throttling background telemetry and update services.
1

Snapshot Your Default OS State

Document Windows 11 build number, active refresh rate, and HDR status before modifying any toggle.

2

Isolate Exactly One OS Toggle

Toggle Optimizations for Windowed Games ON. Do not alter GPU driver settings during the same test.

3

Reboot & Repeat Your Route

Restart the operating system to allow WDDM drivers to re-initialize graphics swapchains cleanly.

4

Revert Immediately if Disproved

If frame pacing standard deviation increases or input feels floaty, revert immediately to baseline.

Microsoft officially documents these as kernel debugging flags, not universal 0.5ms gaming presets. [Ref: 3]

EXPERIMENT 03 // GRAPHICS ARCHITECTURE
RENDER QUEUE MANAGEMENT

Choose your graphics route.

Define your primary objective: absolute lowest local delay, perfect tear-free visual clarity, or an optimal competitive compromise.

ROUTE A // NVIDIA REFLEX NVIDIA

When game supports Reflex: Enable Reflex On inside the game menu. Reflex dynamically paces CPU render submissions just before GPU execution, preventing render queue overflow when GPU load hits 99%.

★ Note: Reflex completely overrides driver-level Ultra Low Latency Mode. Test 'Reflex + Boost' separately to verify GPU clock behavior. [Ref: 1]
ROUTE B // GENERAL / AMD RADEON RADEON

When Reflex is absent: Utilize driver-level Anti-Lag or establish a manual frame-rate cap using the game's internal engine limiter to prevent GPU utilization from locking at 100%.

★ Note: Avoid stacking driver limiters and 3rd party limiters (e.g. RTSS) simultaneously during your comparison run.
Core Question Controlled Comparison Metric to Log
Is workload GPU bound? Lower volumetric shadows and texture effects or set render scale to 90%. Measure GPU utilization % and frame-time stability in intense fights.
Does an FPS cap stabilize latency? Compare uncapped framerate against a cap at your sustainable 99th percentile. Inspect frame-time variance and standard deviation (lower = smoother).
Is screen tearing unacceptable? G-Sync/FreeSync + V-Sync (Driver) + Cap (Hz - 3) vs completely uncapped. Evaluate smoothness vs 1-2ms theoretical input latency trade-off.
The Myth of the Universal "Hz Minus 3" Frame Cap Rule

The "Refresh Rate - 3" rule is strictly valid only when pairing G-Sync/FreeSync with V-Sync to keep the framerate inside the variable refresh rate range. In purely uncapped esports setups or when using NVIDIA Reflex, the Reflex engine automatically manages the optimal cap dynamically.

Write an Empirical Decision: "I retained Setting B because 1% lows improved by 14% and frame-time spikes were eliminated across 3 consecutive runs" is scientific evidence. "It felt crisper" is subjective placebo.

1

Lock DPI & Sensitivity Values

Keep DPI and in-game sensitivity completely untouched throughout the test. Polling rate and movement scaling are independent variables.

2

Test 1,000 Hz Against Higher Supported Rates

Compare standard 1,000 Hz against 4,000 Hz or 8,000 Hz on the same USB port without moving your wireless receiver.

3

Capture High-Speed Arc Sweeps

Record a 60s benchmark while executing continuous high-frequency mouse sweeps. Monitor CPU single-thread DPC/ISR load.

4

Retain the Stablest Telemetry Profile

If 4K or 8K causes frame-time hitching or stutter in CPU-heavy engines, 1,000 Hz remains the rock-solid esports gold standard.

DO NOT CONFUSE POLLING WITH SENSITIVITY

Reporting frequency and distance counts per inch are separate mechanisms. Changing both concurrently invalidates your test data completely.

WIRELESS 2.4GHz RECEIVER PLACEMENT

Position your wireless dongle 15–20cm from the mousepad using the extender cable. Never plug into rear motherboard ports adjacent to noisy USB 3.0 ports.

REPRODUCIBILITY CHECKLIST
PROTOCOL DISCIPLINE

Your next-session checklist.

Execute a disciplined experiment before you queue competitive ranked. Optimization is a deliberate protocol, not random trial-and-error.

01 / Standardize the Scene Route

Select the identical game build, offline custom map, and exact 60-second capture movement pattern.

02 / Snapshot Original Settings

Take full screenshots of your current control panel and in-game settings prior to touching any value.

03 / Quarantine Background Processes

Disable Discord hardware acceleration, browser tabs, antivirus active scans, and cloud sync services.

04 / Change Exactly One Variable

Modify strictly one setting per cycle. Changing two variables simultaneously renders your conclusions completely meaningless.

05 / Record 3 Comparable Passes

Archive all telemetry captures, including passes where performance decreased. Negative data is vital information.

06 / Keep, Revert, or Quarantine

Document the rationale. Stop tweaking immediately if telemetry variance fails to exceed ordinary run-to-run noise.
